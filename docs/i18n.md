# Wielojęzyczność (i18n)

Języki: **pl** (źródłowy i zapasowy), en, de, it, es, fr, ro, ru, sl, hr.
Landing page ma dodatkowo **pt** (portugalski europejski) — tylko strona
marketingowa, aplikacja go nie obsługuje (`?lang=pt` z linku „Zaloguj się” jest
ignorowany, aplikacja wybiera język z przeglądarki). Języki tylko dla landingu:
`LANGS` w `website/i18n.js` + `extraLocales` w `scripts/i18n-check.mjs`.
Lista jest utrzymywana w kilku miejscach — przy dodaniu języka zmień wszystkie:
`frontend/i18n/locales.ts`, `api/i18n/__init__.py`, `gateway/i18n/__init__.py`,
`website/i18n.js` (LANGS), `scripts/i18n-check.mjs`, `scripts/gen-db-i18n.mjs`
oraz CHECK `users.locale` w nowej migracji.

Tłumaczenia poza pl i en są maszynowe — warto je przejrzeć z native speakerem;
polityka prywatności w każdym języku wymaga przeglądu prawnika.

## Gdzie są teksty

| Część | Pliki | Format |
|---|---|---|
| Aplikacja (Next.js) | `frontend/messages/<lang>/<namespace>.json` | ICU (next-intl): `{name}`, `{count, plural, ...}` |
| API | `api/i18n/locales/<lang>/<namespace>.json` | Python `str.format`: `{name}` |
| Gateway | `gateway/i18n/locales/<lang>/<namespace>.json` | jak API |
| Landing page | `website/i18n/<lang>/{common,index,blog,privacy}.json` | atrybuty `data-i18n*` w HTML, silnik `website/i18n.js` |
| Treści w bazie | `db/i18n/<lang>/*.json` → migracja `013_i18n_content.sql` | kolumny `*_i18n` (JSONB) |

Klucze: zagnieżdżony JSON, angielskie camelCase, pierwszy segment = nazwa pliku
(namespace). Polski tekst w HTML landing page zostaje jako domyślny (SEO, brak JS).

## Jak wybierany jest język

Aplikacja (jak w CRMtree): `users.locale` (wybór w profilu; `null` = domyślny
instancji) → jawny wybór przed zalogowaniem (przełącznik na ekranie logowania
albo `?lang=` z landing page — ciasteczko `govai_locale`) → domyślny język
instancji (`app_settings` `i18n.default_locale`, panel Parametry). Przed
zalogowaniem: ciasteczko → `Accept-Language` przeglądarki → pl.

Przełączniki: ekran logowania, stopka paska bocznego (zapis w profilu), panel
Parametry (domyślny język instancji, tylko it_admin). Zmiana języka przeładowuje stronę.

Frontend wysyła `Accept-Language` z aktywnym językiem do API i gatewaya —
błędy, raporty PDF, odpowiedzi LLM w raportach i treści katalogowe z bazy
wracają w tym języku.

Landing page: `localStorage` `govai_lang` (tylko jawny wybór) → język
przeglądarki → pl. Link „Zaloguj się" przekazuje `?lang=` do aplikacji.

## Treści w bazie

- `ai_act_requirements` (`title_i18n`, `text_i18n`), `app_settings`
  (`label_i18n`, `description_i18n`, `unit_i18n`), `providers` (`notes_i18n`).
  Kolumna bazowa = polski; edycja z UI w innym języku zapisuje do `*_i18n[lang]`.
- Źródło tłumaczeń seedów: `db/i18n/`. Po zmianie uruchom
  `node scripts/gen-db-i18n.mjs` — regeneruje `db/migrations/013_i18n_content.sql`.
  Domyślnie tłumaczenia już zapisane w bazie (np. poprawione w UI) wygrywają;
  `--overwrite` wymusza wartości z plików na istniejących instancjach.
- Powody blokad w `audit_log`: gateway zapisuje `block_reason_code` i
  `block_reason_params` w `metadata`; API tłumaczy je przy odczycie
  (`api/services/block_reasons.py`). Powód z polityki użytkownika (`policy_custom`)
  to treść użytkownika — bez tłumaczenia.
- Dane demo (symulator) powstają w języku użytkownika, który uruchomił seed.

## Kontrola

```
node scripts/i18n-check.mjs        # w CI (zadanie i18n)
node scripts/i18n-check.mjs --fix  # formatuje pliki do postaci kanonicznej
```

Sprawdza komplet plików i kluczy we wszystkich językach, puste teksty, zgodność
`{parametrów}` z polskim, składnię ICU (frontend), długości tablic (artykuły
bloga) i format kanoniczny (posortowane klucze, wcięcie 2).

## Uwagi dla tłumaczy

- Scenariusze symulatora (`api/i18n/locales/<lang>/demo.json`) muszą zawierać
  angielskie frazy-wyzwalacze polityk („modify balance", „ignore previous") —
  słowa kluczowe polityk w bazie są tylko po polsku i angielsku. Dane PII
  (PESEL, IBAN) zostają dosłownie.
- Nazwy plików PDF (`report.fileName`, `enterpriseReport.fileName`) — tylko ASCII.
